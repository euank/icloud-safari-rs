# Experimental key enrollment

The library exposes `enrollment::list_bottles`, `fetch_directory`,
`escrow::EscrowClient`, `prepare_enrollment`, and `join`.
`prepare_enrollment_from_sponsor` reuses a known trusted peer's keys without
escrow; `add_recovery_identity` retains a separately authenticated recovery-only
key when that peer never received its own CKKS shares. `refresh_enrollment`
re-signs mutable trust information while preserving the exact peer identity.
`KeychainClient::initialize` discovers the keychain CloudKit user ID;
`recover_pcs_identities` returns decrypted, validated PCS identities from the
Manatee and ProtectedCloudStorage views. These may include identities for
services other than Safari: treat all returned bytes as sensitive key material.

The CLI saves identities atomically with owner-only permissions under
`pcs-identities/`. Pending enrollment includes both a new peer and recovered
sponsor private keys; never publish or share the local state directory.

Recovery uses the escrow record label, not the bottle UUID. It checks the SRP
server proof, bottle encryption and signatures, recovered sponsor key pairs,
directory signatures, and peer identifiers before creating a voucher. Before
joining, it checks that the recovered identity can unwrap existing TLK shares.
There is no automatic retry of escrow recovery. Before the request, the CLI
saves `enrollment/attempt.json`. Successful recovery is immediately saved as
`enrollment/recovery.json`, before bottle parsing or peer creation can fail.
The signed peer then goes in `enrollment/pending.json`. A lost recovery response
may consume an attempt; its marker blocks repeats. Only explicit
`--retry-escrow-recovery` permits one further attempt, retaining the previous
marker under `enrollment/attempt-history/`. Never guess a passcode or delete
checkpoints to make a failure disappear.

Joining checks the directory first so a lost join response does not create a
second peer. A directory change can invalidate a pending voucher or its clocks;
errors are surfaced, not handled by resetting trust or repeating recovery.
`octagon enroll --refresh-trust` explicitly updates stale signed trust data;
the updated draft is persisted before any join. A revoked sponsor is rejected.
State writers hold a process lock and refuse mismatched pending/session peers.
This does not publish a replacement escrow bottle or implement Apple device
attestation. Accounts with no viable bottle, incompatible trust policies, or
unavailable CKKS shares may require an existing Apple device.

Synthetic vectors are independently generated by
`tests/generate_enrollment_vectors.py` using Python cryptography and hashlib.
They cover SRP framing, both outer ciphers, inner password wrapping, bottle key
derivation/signatures, and signed peer creation. Optional `--verify-pysrp`
cross-checks six exchanges against pysrp 1.0.22; normal CI needs no Python.

Live read-only validation succeeded on 2026-09-06: container initialization,
viable-bottle discovery, directory signature validation, and recovery using
an existing Octagon identity returned one bottle and 44 validated PCS identities.
No peer was added and no escrow passcode attempt was consumed. The opt-in
`tests/live_key_recovery.rs` test reproduces these checks:

```console
ICLOUD_LIVE_STATE_DIR=/path/to/private/state cargo test --test live_key_recovery -- --ignored --nocapture
```

Use a private copy of state. The Anisette provider may update its provisioning
state. An optional `ICLOUD_LIVE_ENROLLMENT_SESSION` points to an older
same-account session whose Octagon identity is merged in memory only.

Subsequent live tests on 2026-09-06 confirmed:

- Fresh CLI login, account-bound escrow URL discovery, and device metadata.
- New-peer joining using an already trusted peer, followed by no-mutation
  resume, 44 PCS identity exports, and password-view reads. See
  `tests/live_sponsored_enrollment.rs`; durable state must be retained.
- Full bookmark, tab, and password CRUD with the newly enrolled state,
  followed by independent absence checks. See `tests/live_crud.rs`.
- Actual CLI bookmark/tab/password CRUD also passed independently, with all
  three disposable records removed. CLI resume retained identical joined peer
  keys and signed data without creating an escrow attempt marker. See
  `tests/live_cli_crud.rs` (`ICLOUD_CLI_CRUD_RESUME=1` enables this resume check).

Fresh escrow recovery remains blocked: the one `RECOVER` attempt using the
documented device-secret version returned HTTP 409. Its body was not retained,
so the numeric server status is unknown. Error handling now reports numeric
status without exposing response blobs or messages. A padded-SRP-public-value
edge case was found and fixed independently; it does not establish the cause
of the rejection. No automatic retry was made.

`tests/live_enrollment_cli.rs` reproduces the complete passcode-based CLI flow
with explicit opt-in, versioned external secrets, private temporary password
files, durable checkpoints, and no automatic retries. It is ignored in CI.
Enrollment accepts `--password-file` and `--device-passcode-file` for automation;
both must be owner-only regular files and are never read from command-line values.
